# Нетраннинг — сетевой слой станции

Модуль связывает адресуемые игровые устройства, локальные сети отделов, доступы, взлом,
трассировку, файлы и сетевые сущности. Общий клиент — `/datum/netrun_console` и TGUI
`NetrunTerminal`; NTOS использует то же содержимое через `NtosNetrun`.

[Проверка всего списка требований](REQUIREMENTS.md) отдельно отмечает сделанное в коде,
частично покрытые требования и ограничения. Это описание реализации, а не подтверждение
успешной сборки или игрового прогона.

## Сети и карта

```text
NTnet
└─ гейтвей ЛВС (NET-xxxxx)
   ├─ APC отсека
   │  └─ машины, двери и другие узлы этого отсека
   └─ узлы без подходящего APC
```

ЛВС выбирается через `netrun_lan_for_turf()`: общая, инженерная, медицинская, научная,
снабжения, СБ или командования. Вне станции и шахты создаётся изолированная сеть `ext<Z>`.
Беспроводного маршрута к изолированной сети нет; нужен локальный проводной клиент или
подключение к её узлу.

`/datum/component/netrun_node` даёт атому адрес, тип, защиту, команды, журнал и, при заданной
ёмкости, хранилище. `uplink_node()` связывает обычное устройство с APC его области, если
оба принадлежат одной ЛВС. Это логическая топология карты и Ping: APC не превращается в
отдельную симуляцию физического маршрутизатора, а работоспособность маршрута проверяется
по ЛВС и NTnet.

На одном поле видны достижимые сети. У закрытой сети доступны гейтвей и структурные узлы;
остальные устройства раскрываются после получения доступа. Код `NET-xxxxx` показывается
вместе с информацией о сети, уровнем доступа и наличием ключа. Начальная боковая панель
позволяет выбрать сеть и запустить подбор доступа.

Карта поддерживает поиск по имени, адресу и типу, фильтры типов, значки над узлами, перетаскивание,
масштабирование колёсиком и режим «2 перехода» вокруг выбранного узла. Координаты машин
сохраняют относительное положение; открытие ЛВС, фильтрация и панорамирование не должны
заново перестраивать всё поле. Это схема сети, а не изображение тайлов станции.

`WASD` работает при фокусе самой карты и выбирает узел в нужном направлении.
`Shift+WASD` для сущности ищет работающую доступную цель перехода. Сервер дополнительно
проверяет право входа и задержку между переходами. В текстовых полях эти клавиши остаются вводом.

При перемещении атома узел меняет ЛВС. Периодическая сверка в `SSnetrun` учитывает и
вложенные предметы, которые перемещаются вместе с носителем без собственного сигнала движения.
Перед доставкой отложенного запроса принадлежность узла к сети проверяется заново.

## Точки доступа

| Клиент | Канал и начальная достижимость | Ответ на полную трассировку |
|---|---|---|
| Сетевой терминал | Проводная собственная ЛВС; другие неизолированные сети через рабочую магистраль | Блокировка сеанса |
| Кибердека | Беспроводной NTnet; кабель дополнительно открывает ЛВС выбранной машины | Временное перегорание, разрыв кабеля, ожог держателю |
| Нейролинк | Беспроводной клиент установленного импланта | Урон мозгу и оглушение |
| NTOS | Беспроводной `NetCommander`; `NetBreach` допускает взлом | Разрыв сеанса |
| Сетевая сущность | ЛВС узла-носителя; выход в NTnet из неизолированного сегмента | Урон целостности и потеря доступа |
| pAI | Собственный беспроводной клиент и кнопка «Сеть» | Блокировка клиента и оглушение |
| Интегральная схема | Локальная ЛВС сборки и достижимый NTnet | Только легальные запросы; без взлома и трассировки |

Беспроводным клиентам нужны допустимый Z и работающий ретранслятор NTnet для соответствующего
уровня/связки уровней. Наличие сети в списке не заменяет маршрут к ней.

## Доступ, задержка и журналы

Уровни: `НЕТ < ГОСТЬ < ПОЛЬЗОВАТЕЛЬ < ROOT`.

- ID даёт гостевой вход в ЛВС отдела. Для уровня пользователя учитывается
  `required_access` узла либо штатный `check_access_list()` объекта. При выполнении этих
  условий капитанский или сетевой доступ поднимает уровень до ROOT.
- Файл ключа ЛВС даёт легального пользователя в этой сети. Ключ выпускается
  ROOT-командой `issue_key` на узле, который её поддерживает, например терминале или сервере данных.
  Наличие ключа видно в панели сети; сам секрет не публикуется в общей карте.
- Владелец получает ROOT только к своему поддерживаемому устройству:
  деке/компьютеру в инвентаре, своему нейролинку, своему pAI или endpoint нейроинтерфейса.
  Такое владение не открывает чужие устройства или всю ЛВС.
- Взломанные права хранятся в сеансе. Действия выше легального уровня повышают трассировку.

Команды, оконные действия и опубликованные запросы машин учитывают `latency_to()`.
Прямое подключение к цели имеет нулевую задержку; проводная собственная ЛВС — минимальную;
дальняя связь через NTnet зависит от расстояния и Z. Перед доставкой проверяются маршрут,
оператор, текущая ЛВС, права и состояние цели. Выбранный для команды файл фиксируется по UID
при отправке. Интегральные схемы исполняют свои легальные команды синхронно.

`ping [адрес]` использует тот же расчёт маршрута, что команды, подсвечивает путь
и выдаёт ответ после времени туда-обратно. В общей подсети путь проходит через APC,
между подсетями одной ЛВС — через её гейтвей, между ЛВС — через реле NTnet.
Это игровая модель задержки, а не измерение сетевого соединения клиента с сервером.

Каждый узел хранит собственный ограниченный журнал (`NETRUN_MAX_LOG`), который следует
за устройством при смене ЛВС. `node_log`, карточка и окно узла читают его с уровня пользователя.
Отдельно существуют журнал ЛВС, журнал клиентской консоли и IDS NTnet. На 100% трассировки
добытые права отзываются, сеанс блокируется на минуту и срабатывает реакция носителя.
Журналы модуля не являются постоянным хранилищем между раундами.

## Взлом и прошивка

Обычный Breach Protocol использует матрицу шестнадцатеричных кодов: первый выбор из верхней
строки, затем чередуются столбец и строка. Последовательности в буфере дают пользователя,
ROOT или сброс трассировки. Размер, время и прирост трассировки зависят от защиты;
буфер и программы клиента влияют на условия.

Подбор шлюза учитывает защиту сильнейшего участника ЛВС. По сравнению с машиной
на том же оборудовании матрица шлюза на одну строку/столбец больше, последовательности
доступа длиннее, времени на 5 секунд меньше, а трассировка растёт в 1,25 раза быстрее.
Награда ограничена гостевым доступом к сети; легальные доступы по ID сохраняются.

`firmware` — отдельная атака для API-адаптеров с `allow_emag = TRUE`.
Нужны уже полученный ROOT и `icepick.exe`. Атака задаёт защиту 5, матрицу 7×7,
до 7 ячеек буфера и 20 секунд. Успешная ROOT-последовательность вызывает штатный
`emag_act(operator)` машины и добавляет трассировку. Прямого выставления `EMAGGED`
всем объектам нет: ограничения и результат конкретного `emag_act` сохраняются.

## Карточки, вкладки и API машин

Карточка выбранного узла и его вкладка используют общий `command_entries(console)`:
одинаковые команды, доступность, описания и подробную справку. Вкладки открываются и
закрываются для видимых узлов; одновременно хранится до пяти, при открытии следующей
вытесняется самая старая. Содержимое зависит от возможностей конкретного устройства.

Механики без отдельного TGUI задаются сетевыми командами и оконными хуками. Для части машин
есть `/datum/netrun_api`: декларативный адаптер публикует `ui_static_data()`/`ui_data()`
и разрешённые вызовы штатного `ui_act()`. Сейчас адаптеры описывают управление переносной
турелью, выдачу товара, часть действий РнД-консоли и производство. Для шлюзов, APC и ботов
есть разрешение атаки прошивки; обычное управление шлюзом/APC остаётся специализированными
сетевыми командами.

**Нативный интерфейс встроен частично.** `RemotePanel` выводит дерево данных и кнопки
опубликованного API. Он не монтирует исходный React/TGUI-интерфейс машины. Не каждый
`ui_act` в билде автоматически доступен по сети. Разрешённые действия и параметры
задаются адаптером; неизвестные действия отклоняются, лишние параметры отбрасываются.
Ресурсы, исследования, блокировки, оплата и другие внутренние проверки машины продолжают
действовать. Запрос не выдаёт мобу административных или силиконных привилегий.

## Файлы, память и Фаза F

Хранилище клиента и подключённый шард содержат `/datum/netrun_file`.
На поддерживаемых узлах есть отдельная удалённая память.

| Тип | Содержимое и использование |
|---|---|
| `text` | Текстовые документы; чтение, создание, редактирование и печать |
| `key` | Легальный пользовательский доступ к одной ЛВС |
| `daemon` | Идентификатор программы из реестра демонов |
| `techweb` | Дамп идентификаторов исследованных технологий |
| `techweb_link` | Переносимая weakref-привязка к живой исследовательской сети |
| `photo` | Настоящий `/datum/picture` с пикселями и подписью |

В интерфейсе выбирается конкретный UID, поэтому одинаковые имена не подменяют файл.
Можно читать и переименовывать файлы, создавать/редактировать текст, копировать и перемещать
данные между локальной памятью и шардом. Перемещение сохраняет UID и передаёт владение;
копия получает новый UID, а фото — независимый снимок. Проверка ёмкости выполняется до
переноса. Текст ограничен 10000 символов и занимает не меньше одной ячейки
(одна ячейка на каждые начатые 500 символов).

Загрузка с узла и на узел требует пользователя и работающего маршрута; удаление на узле —
ROOT. Демоны работают из локальной памяти или подключённого шарда автоматически.

Фаза F теперь включает следующие цепочки:

1. `cam_photo` работающей камеры использует штатный `camera.captureimage()` и сохраняет
   реальный кадр по дальности и видимости камеры в `photo`: обычно 15×15 клеток и 4 ячейки
   памяти, максимум 21×21 и 7 ячеек. Между кадрами — 5 секунд. Стены и XRay учитываются
   штатным списком видимости камеры; кэш снимка удерживает исходные appearance до конца рендера.
   Файл можно перенести на шард, просмотреть и распечатать.
2. `pc_print` на модульном компьютере печатает **выбранный** текст либо фото. Нужны исправный
   принтер и бумага; фотография становится обычным `/obj/item/photo`, текст — листом бумаги.
3. `rnd_grab` снимает дамп исследованных технологий с сервера, `rnd_push` импортирует
   **выбранный** дамп в его текущую исследовательскую сеть. Это копирование знаний,
   а не перенос живой привязки. `rnd_siphon` сохраняет текстовый отчёт и списывает
   25% очков только после успешного размещения файла.
4. `web_copy` на узле с `techweb_holder` создаёт файл `techweb_link`.
   Перенесите его на другой клиент, выберите и вызовите `web_bind` на поддерживаемой машине.
   Привязка меняется через `COMSIG_ATOM_SET_TECHWEB`; исходная сеть не копируется.
   Weakref действует, пока существует исходный техвеб, и не сохраняет его жизнь сама.
   Это не постоянный межраундовый пароль.

Прежнее описание «фото и переносимая привязка ещё не сделаны» более не соответствует коду.

## Демоны и получение оборудования

`/datum/netrun_daemon` задаёт имя файла, размер, эффект и тип бонуса. Реестр `SSnetrun`
обнаруживает подтипы; клиент выбирает самый сильный бонус каждого вида, копии не складываются.

| Программа | Память | Эффект |
|---|---:|---|
| `buffer.exe` | 2 | +1 ячейка буфера |
| `icepick.exe` | 3 | −1 уровень защиты при обычном подборе; необходим для атаки прошивки |
| `cloak.exe` | 3 | −30% прироста трассировки |

Исследование `netrunning` открывает базовую инфраструктуру, деку, шард и отдельный шард
`buffer.exe`. `netrunning_neural` открывает нейролинк, семя, военную деку и шарды
`icepick.exe`/`cloak.exe`. Для программ есть реальные дизайны печати на протолате.
Готовый `/obj/item/netrun_shard/daemons` с полным набором также остаётся типом предмета;
это не отдельный установщик программ. Каталог и наличие программ показывает `daemons [id]`.

## CLI и справка

История ввода сохраняет до 20 последних строк в текущем интерфейсе; ↑/↓ перемещаются по ней,
Tab дополняет команду и доступные аргументы. Многострочный вывод сохраняет переносы строк.

| Команды | Назначение |
|---|---|
| `help [команда]`, `info`, `clear` | Автосправка, состояние сеанса, очистка журнала клиента |
| `net [код или id]`, `nodes`, `sel <адрес>` | Сети и выбор узла |
| `open [адрес]`, `close [адрес]` | Вкладки узлов |
| `run <команда>`, `scan`, `ping [адрес]`, `breach [адрес или код]` | Действия и подбор доступа |
| `ls`, `mem`, `rm <имя>`, `daemons [id]` | Файлы, ёмкость и программы |
| `chat <текст>` | Канал `#noosphere` |

`help` и дополнение строятся из `/datum/netrun_cli_command`:
`id`, `args`, `desc`, `category`, `detailed_help()`, `completions()`.
`help run` и `help <id команды узла>` читают актуальные команды выбранного узла,
включая динамические. Подробности сетевой команды строятся из её `desc`, `help`,
уровня доступа, трассировки и задержки; тексты не нужно повторять в отдельном CLI-switch.
Операции создания/редактирования и выбора UID сейчас представлены файловой панелью;
CLI не реализует полноценную файловую оболочку.

## Сущности, камеры и звук

`/mob/camera/netrun_entity` живёт в узле-носителе. Войти в другой узел можно при работающей
связи и уровне пользователя, с паузой между переходами. Стрелки в игровом мире ищут
подходящий соседний узел своей ЛВС; навигация по карте описана выше.

Сущность видит мир через устройства с оптикой. Общие хуки `netrun_view_capable()`,
`netrun_view_target()` и `netrun_view_settings()` поддерживают работающие камеры,
исправные кибернетические глаза носителя и надетые HUD-очки после обхода прошивки.
Очки публикуются отдельным узлом; глаза используют узел кибернетики носителя.
Требуется пользовательский доступ. Учитываются настройки зрения самой оптики.

Оконное действие «Смотреть» подключает поток с приоритетом над зрением узла-носителя,
не перемещая сущность. Поток проверяется каждый тик; отключение камеры, снятие очков,
подавление глаз или потеря прав разрывают просмотр. Без доступной оптики сущность слепа.
Текстовая сводка в окне дополняет настоящий игровой обзор.

Сущность сама по себе не слышит речь. Интерком с активной сущностью или подписанной
консолью передаёт местную речь при включённом микрофоне либо скрытой записи;
радиоприём зависит от включённого динамика. `listen` подписывает консоль на поток,
`audio_log` читает последние реплики, `audio_tap` включает скрытую запись на две минуты.
Речь сущности через интерком использует его обычный радио/локальный вывод.

Есть погружение через нейролинк с оставленным без сознания телом и гост-роль из семени.
Урон телу может аварийно завершить погружение. Сервер с семенем появляется при старте
раунда через `SSnetrun.roundstart_seeds`. `purge` на поддерживающем узле наносит
посторонним процессам 45 урона и выталкивает выживших. Сущность может переименоваться,
пользоваться виртуальным мессенджером и общим каналом NTNRC `#noosphere`.

## Нейроинтерфейсы и pAI

Нейролинк подключает панель состояния, монитор связи и сетевое зрение к существующему
`/datum/component/neural_interface`. Сущности и pAI получают тот же тип панели через
`/datum/component/netrun_neural_feedback`. Компонент использует штатные сигналы
записи журнала/данных и собственные события `COMSIG_NETRUN_CONSOLE_EVENT`,
`COMSIG_NETRUN_ENTITY_NODE_CHANGED`, `COMSIG_NETRUN_ENTITY_INTEGRITY`,
`COMSIG_NETRUN_ENTITY_TICK` для связи, целостности, переходов и трассировки.
Панель NETLINK располагается под DATA. Её надписи и события используют ASCII для
совместимости с HUD-шрифтом; имена и тексты транслитерируются только при выводе,
исходные имена устройств и содержимое файлов сохраняются.

Сам нейроинтерфейс публикуется отдельным невидимым
`/obj/effect/netrun_endpoint/neural`, который несёт свой `netrun_node` и следует за носителем.
Его жизнью управляет `/datum/component/netrun_neural_adapter`.
Это не второй компонент узла на человеке: кибернетика носителя остаётся отдельной целью.
Команды endpoint: состояние, отправка выбранного текста в журнал/панель,
отметка источника и ROOT-переключение экрана. Подсистемы вывода продолжают учитывать
наличие соответствующих модулей нейроинтерфейса.

pAI имеет собственный клиент и узел в карте и мобильной оболочке, батарею и кнопку «Сеть».
Его сетевой клиент возвращает пустой список обычных ID-доступов: принадлежность к силиконам
не делает pAI администратором станции. Собственный узел доступен ему по владению.

## Другие интеграции

- Реальные модульные компьютеры, включая КПК/планшеты, становятся узлами.
  Виртуальные PDA сущности и pAI исключены. Доступны список программ, завершение активной
  программы, выключение и печать выбранного файла; это не удалённый запуск любой программы ОС.
- Нейролинк и дека регистрируются через `netrun_access_device`; чужой клиент можно
  диагностировать и временно отсоединить с достаточными правами.
- Органы публикуют адресные команды через `netrun_hacks()`/`netrun_hack()` и
  `/datum/netrun_command/organ`: например, `heart_stop@heart`. У каждого органа — свои механики.
- Борги поддерживают блокировку шасси; ИИ — временное глушение управления.
  Оконные двери, мулботы, интеркомы, телекомы и ретрансляторы имеют свои команды.
- WEB показывает каталог и текст страниц из кэша `SSntnet` при наличии NTnet.
  Встраивание интерактивных страниц и вызов игровых API с сайтов не реализованы.

## Расширение и границы модуля

| Задача расширения | Контракт |
|---|---|
| Добавить цель | `AddComponent(/datum/component/netrun_node, ...)`; при необходимости `netrun_name()`, `netrun_online()`, `netrun_status()` |
| Добавить сетевую команду | Подтип `/datum/netrun_command` с метаданными и `execute()`; включить id в команды узла |
| Команды от установленного компонента | `netrun_extra_commands()`; результат объединяется в `all_command_ids()` |
| Личный доступ | `netrun_owner_access(console)`; право ограничено конкретным атомом |
| Особое окно | `netrun_window_fields/actions/feed/act`; права и доставка проверяются консолью |
| Источник видеопотока | `netrun_view_capable/target/settings`; общие оконные действия, проверка связи и управление перспективой |
| Опубликовать штатное управление | Подтип `/datum/netrun_api`: `atom_type`, `interface_name`, схемы `actions`, при необходимости `allow_emag` |
| Добавить CLI-команду | Подтип `/datum/netrun_cli_command` с описанием и completion/help |
| Добавить программу | Подтип `/datum/netrun_daemon`; для физического получения — шард/дизайн исследования |
| Подключить клиент или обратную связь | Компоненты `netrun_access_device`, `netrun_neural_adapter`, `netrun_neural_feedback` |

Регистрация новых подтипов CLI, демонов и API выполняется реестрами, без дописывания общего
switch консоли. Для новой сетевой команды обычно достаточно подтипа и регистрации её id у цели.
Новый особый интерфейс или тип данных может потребовать своего TGUI-компонента: декларативный
API не обещает автоматически воспроизвести любой существующий GUI.

Файлы: `core/` — сеть, права, запросы, реестры, файлы и CLI;
`targets/` — механики устройств; `integration/` — API, нейроинтерфейс, pAI, NTOS и исследования;
`entity/` — сущности; `items/` и `machines/` — носители и окна.

Из старого плана реализованы основа, кибернетика/силиконы, часть инфраструктуры, просмотр
сайтов и перечисленные цепочки Фазы F. Оцифровка экипажа, специальный антагонист-сущность,
экономика торговли данными, полное покрытие машин API и исходные GUI всех устройств
остаются отдельными задачами. Состояние проверок следует оценивать по текущим диагностическим
выводам, а не по этому списку возможностей.
